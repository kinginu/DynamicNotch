### [high] Tray range selection slices _files with a stale base index after a removal

- 場所: `DynamicNotchApp/Sources/Tray.swift:728`（視点: crash-safety、判定: 維持 / 維持）
- 要約: selectFile's plain-click branch (line 728) and handleShiftArrowSelection (line 398; line 389 also stores the unclamped stale lastIdx as the new base) compute Array(_files[minIdx...maxIdx]) from _baseFileIndex/_lastSelectedIndex, but removeFile (hover X button, context-menu Remove, drag-out removal) and the FolderMonitor prune in updateFiles never reset those indices, so the slice upper bound can exceed _files.count - 1 and trap. Only removeSelectedFiles/selectFile(nil)/removeAll reset them.
- 失敗シナリオ: Tray holds 3 files. Click file 3 (base = last = 2). Hover file 3 and click its X (TrayFileView.swift:84 → removeFile; indices untouched; 2 files remain). Click file 1 → selectFile: baseIdx = 2, clickIdx = 0 → _files[0...2] on a 2-element array → 'Range requires upperBound <= endIndex' trap. Same with Shift+↓ after that removal: selectedFiles is empty so last = 0, newIdx = 1, base is still 2 → _files[1...2] trap. Deleting a tray file in Finder (updateFiles prune) triggers the same stale state.
- 推奨修正: Clamp or re-derive indices before slicing: in selectFile/handleShiftArrowSelection compute base via _files.firstIndex(of:) of a stored anchor TrayFile (or clamp baseIdx/lastIdx to 0..._files.count-1 and bail when _files is empty). Also reset _baseFileIndex/_lastSelectedIndex in removeFile, updateFiles and unstack. Note the non-shift branch range-selects on a plain click whenever a base exists; probably should be the shift branch.

### [high] CameraManager state mutated from a concurrent global queue; setupSession/stopRunning race on the sessions dictionary

- 場所: `DynamicNotchApp/Sources/CameraManager.swift:179`（視点: concurrency、判定: 反証 / 維持）
- 要約: CameraManager is an @Observable class whose `_sessions`/`_allDevices` dictionaries are read and written (`captureSession(for:)` inserts at line 179, `stopRunning(for:)` removes at line 323, plus `access(keyPath:)` observation registrations) with no synchronisation, yet MirrorWidgetView calls `setupSession` and `stopRunning` from `DispatchQueue.global(qos: .userInitiated).async` (MirrorWidgetView.swift:133 and :144). Two such blocks run concurrently on the global concurrent queue, so a quick open/close of the Mirror widget (or `autoOpen` on appear followed by the notch closing) mutates the same Swift Dictionary from two threads and calls beginConfiguration/removeInput/startRunning and stopRunning on the same AVCaptureSession simultaneously.
- 失敗シナリオ: Mirror widget with autoOpen on: notch opens → onAppear dispatches setupSession (thread A); user moves the pointer away within ~100 ms → onDisappear dispatches stopRunning (thread B). A is inside `_sessions[key] = (session, output)` while B executes `_sessions.removeValue(forKey:)` → Swift exclusivity/heap corruption crash, or B's `removeValue` wins first and A then `startRunning()`s a session that is no longer tracked, leaving the camera running (green light on) with no way to stop it. Also `sessions[...]` is read off-main at MirrorWidgetView.swift:135 while A writes it.
- 推奨修正: Give CameraManager a private serial `DispatchQueue` (or make it an actor) and perform all session setup/teardown and dictionary mutation on that queue; have MirrorWidgetView call manager methods that internally hop to that queue and deliver the AVCaptureSession back on main. Keep @Observable mutations (`_sessions`, `_allDevices`) on the main thread (e.g. publish a main-thread copy) so observation callbacks do not fire from a worker thread.

### [medium] Mirror camera start and stop run concurrently on the global queue and race on CameraManager._sessions / the same AVCaptureSession

- 場所: `DynamicNotchApp/Sources/CameraManager.swift:265`（視点: crash-safety、判定: 維持 / 反証）
- 要約: MirrorWidgetView.setupCamera (line 148) and stopCamera (line 159) both dispatch onto DispatchQueue.global(qos: .userInitiated), a concurrent queue. setupSession mutates the @Observable dictionary _sessions (lines 179, 265) and runs beginConfiguration/addInput/commitConfiguration/startRunning, while stopRunning (line 282) can simultaneously remove inputs/outputs and removeValue(forKey:) (line 323) on the same key. Swift Dictionary is not safe for concurrent mutation, and AVCaptureSession must not be reconfigured from two threads; additionally setupSession's trailing startRunning can run after stopRunning removed the entry, leaving an orphaned running session (camera stays on).
- 失敗シナリオ: Mirror widget with 'Open camera automatically' (or a tap) starts the camera; the user closes the notch within the ~0.5–2 s that AVCaptureSession.startRunning takes. onDisappear → stopCamera dispatches stopRunning on another worker thread while setupSession is between captureSession(for:) and line 265: concurrent write/remove on _sessions (heap corruption / EXC_BAD_ACCESS) and concurrent configuration of one AVCaptureSession; in the benign ordering the session is removed first and then started, so the camera indicator stays lit with no owner.
- 推奨修正: Serialize all CameraManager session work on a private serial DispatchQueue (or make setupSession/stopRunning @MainActor and offload only startRunning/stopRunning), and have startCamera's completion re-check mode before keeping the session (it does) plus have stopRunning cancel a pending setup via a generation token.

### [medium] Closed-notch timer-expired live activity is lost when NookTimersStore.tick marks the timer expired before NookTimerExpiryMonitor's armed Timer fires

- 場所: `DynamicNotchApp/Sources/LiveActivities/`（視点: concurrency、判定: 維持 / 維持）
- 要約: `NookTimerExpiryMonitor` re-reads `nook_timers_snap` on every `UserDefaults.didChangeNotification` and `rearm()` starts by invalidating the pending one-shot `armed` timer (line 369) and only re-arms for entries whose state is still "running". `NookTimersStore.shared` is now app-lifetime (AppDelegate.swift:53) and its 0.5 s `tick()` sets the expired entry to `.cancelled` and `save()`s (NookTimersStore.swift:278-284, 307) at the first tick after `expiresAt`. The monitor's timer fires at `expiresAt` with `tolerance = 0.2`. Whichever runs first wins: if the store's tick lands first, the resulting defaults change calls `reload()` → `rearm()`, which invalidates the monitor's timer and drops the entry (no longer "running"), so `onExpired` is never called and no `.timerExpired` activity is shown. The comment at line 329 still assumes the store only exists while the notch is open, which is no longer true.
- 失敗シナリオ: Start a 1-minute Nook timer, close the notch. The expiry falls at T; the store's tick occurs at T+0.05 s (tick phase is arbitrary, so this happens for roughly one timer in five), the monitor's timer with 0.2 s tolerance is scheduled for T+0.15 s. Tick writes state=cancelled → UserDefaults notification → `rearm()` invalidates the armed timer → the closed notch never shows "Timer ended"; only the sound plays.
- 推奨修正: Drive the live activity directly from the store: have `NookTimersStore.tick()` call `LiveActivityCenter.shared.showTimerExpired(label:)` (or post a notification the center observes) when it flips an entry to expired, and delete `NookTimerExpiryMonitor`. If the snapshot-watching design is kept, in `rearm()` announce any entry that disappeared from the running set with an `expiresAt` within the last few seconds instead of silently dropping it.

### [medium] TrayFile's dispatch-source cancel handler captures self weakly, so the directory file descriptor is never closed after dealloc

- 場所: `DynamicNotchApp/Sources/TrayFile.swift:349`（視点: concurrency、判定: 維持 / 維持）
- 要約: `startObservingFileChanges_internal()` opens the item's parent directory (`fd`, line 323) and installs a `DispatchSource.makeFileSystemObjectSource` whose cancel handler closes `self._fileDescriptor` only `if let self` (lines 349-356). `deinit` cancels the source (line 406), but dispatch cancel handlers run asynchronously on the target queue after `cancel()` returns, i.e. after the TrayFile has been deallocated, so `self` is already nil and `close()` never runs. Every TrayFile that goes away (removed from the tray, pruned by `updateFiles`, duplicate instances rejected by `Tray.addFile`'s inode check, instances created in `adoptFiles`/`addFilesFromURLs`) leaks one fd plus the retained DispatchSource.
- 失敗シナリオ: Add 10 files to the tray and clear it, repeatedly, during a long-running session: each cycle leaks 10 directory fds. Once the process hits its open-files limit, `FileManager.copyItem` in `addFilesFromURLs`, `Data.write` in `persist()`, QuickLook thumbnails and the next `open()` in this very function (`fd < 0` → silently no watch) start failing, with no error surfaced to the user.
- 推奨修正: Capture the descriptor by value: `let fd = fd; source.setCancelHandler { Darwin.close(fd) }` (as FolderMonitor.swift:46-48 already does), and reset `_fileDescriptor = -1` in `stopObservingFileChanges_internal()`.

### [medium] Media-key event tap is added to a GCD worker thread's run loop that is never run, so the active tap is never serviced

- 場所: `DynamicNotchApp/Sources/MediaKeyTapInternals.swift:176`（視点: concurrency、判定: 維持 / 維持）
- 要約: `startKeyEventTap` dispatches a block to a private queue that captures `CFRunLoopGetCurrent()`, adds the CFMachPort source to it and enables the tap (lines 176-188) but never calls `CFRunLoopRun()`; the block returns and the worker thread goes back to the pool, so the stored `runLoop` is never spun. Consequences: the tap callback (`tapCallback`/`process`) never executes, `enableTap`'s `CFRunLoopPerformBlock` + `CFRunLoopWakeUp` (lines 58-64) target a run loop that never drains its block queue, and the `tapDisabledByTimeout` re-enable at line 88 can never run. Because the tap is created with `.defaultTap` (an active, synchronous filter) for mask 0x4400 (keyDown | NX_SYSDEFINED), the WindowServer must wait on this unserviced port for every matching event until it gives up and disables the tap. `VolumeAndBrightnessListener.start()` is invoked from NotchView.swift:745 whenever Live Activities are enabled.
- 失敗シナリオ: On a machine where the app has Input Monitoring/Accessibility (needed for `CGEvent.tapCreate` to succeed) and Live Activities enabled: after launch, every key press and media key system-wide is delayed by the event-tap timeout until macOS disables the tap; afterwards the volume/brightness keys never reach the delegate at all. Without the permission `tapCreate` returns nil and `start()` silently returns, masking the bug.
- 推奨修正: Run the loop on a dedicated thread, as the original MediaKeyTap library does: inside the queued block call `CFRunLoopRun()` after `tapEnable`, and make `stopWatchingMediaKeys` stop that run loop (it already calls `CFRunLoopStop`). Alternatively drop the private queue and add the source to the main run loop (`CFRunLoopGetMain()`, `.commonModes`), setting `runLoop = CFRunLoopGetMain()`.

### [medium] attemptHUD() leaks a repeating 3.3 s Timer and wake observers on every start()/wake

- 場所: `DynamicNotchApp/Sources/VolumeAndBrightnessListener.swift:103`（視点: perf-memory、判定: 維持 / 維持）
- 要約: attemptHUD() creates a new repeating Timer.scheduledTimer(3.3 s) and assigns HUDCloseTimer without invalidating the previous one; startObservingSystemWake() (lines ~122-142) likewise overwrites systemWakeUpObserver/screenWakeUpObserver without removing the old tokens. start() is not idempotent past the MediaKeyTap guard and is called from NotchView.SideEffectsModifier.onAppear for every notch window (NotchView.swift:745), so with 3 screens there are already 3 live repeating timers and 6 wake observers; every NSWorkspace.didWake / screensDidWake then fires all registered observers, each calling attemptHUD() and leaking yet another repeating timer. Repeating timers are retained by the main run loop until invalidated, so the count grows without bound across sleep/wake cycles.
- 失敗シナリオ: Launch with 3 displays (3 timers, 6 observers). Each sleep/wake adds 6 more never-invalidated repeating timers; after ~100 wake cycles the main run loop services ~600 timers firing every 3.3 s (empty bodies, but each is a run-loop wakeup and a retained object), and each wake fans out to hundreds of attemptHUD() calls.
- 推奨修正: In attemptHUD() call HUDCloseTimer?.invalidate() (and HUDCloseWorkItem?.cancel()) before creating a new one; guard startObservingSystemWake() with `guard systemWakeUpObserver == nil` (or remove existing tokens first); make start() a no-op when already started.

### [medium] Two full-artwork TIFF encodes on the main thread for every MediaRemote event

- 場所: `DynamicNotchApp/Sources/MediaManager.swift:505`（視点: perf-memory、判定: 維持 / 維持）
- 要約: updateTrackInfo() dedupes artwork with `old.tiffRepresentation == new.tiffRepresentation`. The adapter (MediaRemoteAdapter.m:420, 0.1 s debounce) emits a payload with the full base64 artwork on every kMRMediaRemoteNowPlayingInfoDidChangeNotification and TrackInfo decodes a fresh NSImage per event, while Track == compares albumArtImage by identity (Track.swift:76), so this compare runs for every event (play/pause, seek, progress updates). tiffRepresentation builds an uncompressed bitmap of w*h*4 bytes (about 1.4 MB at 600x600, 5.8 MB at 1200x1200) for both images, on the main thread, even when preservingArtworkIfDowngrade already returned the identical NSImage object.
- 失敗シナリオ: Music/Spotify playing with 1200x1200 artwork: each now-playing update (several per minute, bursts on seek/skip) allocates and encodes ~12 MB of TIFF data and byte-compares it on the main thread inside the SwiftUI update, causing allocation churn and frame hitches in the notch.
- 推奨修正: Compare the raw payload instead: keep lastReceivedTrackInfo?.payload.artworkDataBase64 (or its count + hash) and reuse the previous NSImage when the base64 string is equal; also short-circuit when `old === new`.

### [medium] Display scaling/resolution change leaves the notch window with the old hardware notch size

- 場所: `DynamicNotchApp/Sources/WindowsManager.swift:307`（視点: startup-lifecycle、判定: 維持 / 維持）
- 要約: `updateWindows()` re-frames existing kits via `setupDynamicNotchWindow()`, but when `dynamicnotchWindow != nil` only `notchGeometry.update(screen:)`/`fit` run and the method returns. The `RootView` was built once with `screenNotchSize: screen.hardwareNotchSize` (line 324) and injects it as `\.notchSize`; it is never rebuilt or updated. `hardwareNotchSize` derives from `safeAreaInsets`/`auxiliaryTop*Area`, which change in points whenever the built-in display's scaling ("More Space"/"Larger Text") changes, and when a screen is re-identified as a notch-less display (menu-bar pseudo notch).
- 失敗シナリオ: MacBook built-in display at default scaling (notch ≈ 32 pt high) → user switches to "More Space" in System Settings → `didChangeScreenParameters` → `updateWindows()` repositions the window but the closed notch, live-activity row and footprint keep the previous point size, so the drawn notch no longer matches the camera housing until the app is relaunched (the display ID does not change, so the kit is never torn down).
- 推奨修正: In `setupDynamicNotchWindowOnMain` compare the new `screen.hardwareNotchSize` with the one the hosted RootView was built with and recreate the hosting view/RootView (or make `notchSize` observable state that WindowsManager updates) when it differs.

### [low] TrayFile directory file descriptor leaks: dispatch-source cancel handler captures weak self and runs after deinit

- 場所: `DynamicNotchApp/Sources/TrayFile.swift:349`（視点: crash-safety、判定: 維持 / 維持）
- 要約: startObservingFileChanges_internal opens the parent directory (O_RDONLY) and stores the fd in _fileDescriptor; the source's cancel handler closes it only via `if let self`. The only cancel() call is from deinit (line 366), by which time the weak reference is already nil when the handler runs asynchronously on main, so close() is never called and one directory fd leaks per TrayFile that goes away (remove, clear, prune, rename replacing the instance).
- 失敗シナリオ: Long-running session with keepFilesAfterQuit and frequent drop/remove cycles (or many files in a stack cleared repeatedly): each removed TrayFile leaves an open directory fd; eventually open()/socket/file APIs elsewhere fail with EMFILE (tray copies, SwiftData, thumbnails). Also keeps external volumes marked 'in use' for by-reference items.
- 推奨修正: Capture the fd value (let fd = self._fileDescriptor) in the cancel handler instead of self, as FolderMonitor.swift already does, and open the directory with O_EVTONLY.

### [low] NoteEditorWindows adds a block-based willClose observer per open and never removes it

- 場所: `DynamicNotchApp/Sources/Support/Ext-A.swift:159`（視点: crash-safety、判定: 維持 / 反証）
- 要約: NotificationCenter.default.addObserver(forName: NSWindow.willCloseNotification, object: window, queue: .main) returns a token that is discarded, so the observer (and its captured id) stays registered forever; each note open after a close registers another one. The window itself is isReleasedWhenClosed = false and is dropped from `windows`, so this is a steady leak rather than a dangling reference, but it is one more observer per open.
- 失敗シナリオ: Open and close the same or different notes repeatedly over a session: NotificationCenter accumulates one never-removed observer per open; memory grows and each old observer still filters on a dead window object pointer.
- 推奨修正: Store the token alongside the window (e.g. windows[id] = (window, token)) and removeObserver(token) inside the willClose handler, or make NoteEditorWindows the window's delegate and implement windowWillClose.

### [low] FullscreenMonitor flags every screen as fullscreen once Accessibility is granted (wallpaper window matches, coordinates mismatched)

- 場所: `DynamicNotchApp/Sources/FullscreenMonitor.swift:125`（視点: startup-lifecycle、判定: 維持 / 維持）
- 要約: `getFullscreenStates()` calls `CGWindowListCopyWindowInfo(.optionOnScreenOnly, …)` without `.excludeDesktopElements` and without filtering `kCGWindowLayer == 0`, so the Dock's wallpaper window (exactly the display bounds) is in the list and matches the screen frame on the main display → `isFullScreen` is permanently true, and the real fullscreen transitions produce no change. In addition the comparison mixes CG window bounds (top-left origin, y down) with `NSScreen.frame` (bottom-left origin, y up), so on any secondary display not aligned at y = 0 real fullscreen windows never match. The code is gated on `AXIsProcessTrustedWithOptions(nil)`, so it only misbehaves after the user grants Accessibility (which the tray's key monitor needs).
- 失敗シナリオ: User grants Accessibility → `fullScreenStateDict` is all-true from init → `NotchView.isDisabledDueToFullScreen` is true from the start, `nonNotchHeight` is 0 and the "close the notch when a fullscreen app appears" reaction never fires again because the value never changes; on an external display above the main one, a genuine fullscreen app is never detected either.
- 推奨修正: Pass `[.optionOnScreenOnly, .excludeDesktopElements]`, skip entries whose `kCGWindowLayer != 0` (and the app's own windows), and convert CG bounds to Cocoa coordinates (flip y using the main screen height) before comparing with `screen.frame`.

### [low] Fan polling pause can get stuck while a second screen's Nook is still visible (widget onDisappear overrides the host hook; display disconnect never re-evaluates)

- 場所: `FanControl/DynamicNotchIntegration/FanControlWidgetView.swift:58`（視点: startup-lifecycle、判定: 維持 / 維持）
- 要約: The host hook (NotchView.swift:427-430) computes visibility across all screens (`DynamicNotchState.anyScreen(in: .nook)`), but the widget's own `.onDisappear` still calls `setMonitoringPaused(true)` whenever `pauseWhenNookHidden` is on. Because the Nook content is removed with `.transition(.opacity)` inside `withAnimation`, `onDisappear` runs after the host hook, so closing one screen's Nook while another screen's Nook stays open ends in the paused state although a widget is visible. Conversely, `DisplayKit.cleanup()` (WindowsManager.swift:261) removes a screen whose notch was `.nook` without calling the hook, leaving monitoring un-paused with no Nook shown.
- 失敗シナリオ: Two displays, Fan Control enabled with "Pause When Nook Is Hidden": open Nook on display A, open Nook on display B, close B → hook: still visible (A) → unpaused; ~0.35 s later B's `FanControlWidgetView.onDisappear` → `setMonitoringPaused(true)` → the widget on A updates only at the slow paused rate (or not at all when alerts are off) until some notch mode changes again.
- 推奨修正: Drop the widget's own `onDisappear` pause when the host hook is present (or make it re-evaluate `anyScreen(in: .nook)` instead of unconditionally pausing), and call `FanControlNookVisibility.nookVisibilityChanged(isVisible: DynamicNotchState.anyScreen(in: .nook))` from `DisplayKit.cleanup()` after removing the screen's state.
